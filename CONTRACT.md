# The UnderlineKit contract

iRead talks to this package through one module, `UnderlineKit`, and nothing else. That module is the contract: what iRead sends in, what it gets back, and what every value means. Everything behind it, the pipeline in `Sources/UnderlineEngine/`, can change freely as long as the contract holds.

This file says what the contract is, which changes break it, and what to do for each kind of change.

## 1. What is the contract

Everything under `Sources/UnderlineKit/`, and the tests that guard it under `Tests/UnderlineKitTests/`.

| File | What it promises |
|---|---|
| `Underlining.swift` | The protocol an app depends on: `version`, `summary`, `underlines(inChapter:of:startingAt:)` |
| `BookSource.swift` | What the engine needs from the app: `BookSource`, `ChapterText` (and `BookText` for tests) |
| `UnderlineResult.swift` | What comes back: `UnderlineResult`, `UnderlineBatch`, `ConsideredPhrase` |
| `Underliner.swift` | The real engine behind the protocol, and its presets `.release` and `.testing` |
| `StubUnderliner.swift` | A fake for an app's tests: no engine, no download |

**Not the contract:** everything under `Sources/UnderlineEngine/` (`UnderlineCtrl`, `Linker`, `LinkMethod`, the rules, the embedding, the knobs). An app must not import `UnderlineEngine` directly. Today its types are still `public`, so only this rule stops it (see §7).

## 2. What the values mean

A change to any of these is a contract change, even when no type changes and everything still compiles. These are the breaks the compiler can't catch.

**Going in (`BookSource`, `ChapterText`)**
- `id`: any stable ID of the book. The engine keeps per-book work (word counts) under it. iRead passes the book's fingerprint.
- `chapterText(_:)`: chapter indexes are 0-based.
- Paragraph and sentence `index`es are the **app's global indexes** across the whole book, not per chapter.
- A sentence's `range` is **within its paragraph's text**, in **UTF-16** units.

**Coming out (`UnderlineResult`)**
- `id`: stable for the same underline, so an app can tell an underline it already has.
- `sentence`, `paragraph`: global indexes, as above.
- `range`: the underlined phrase, within its paragraph, UTF-16.
- `text`: the phrase itself.
- `kind`: one of `"action"`, `"reaction"`, `"feeling"`, `"outcome"`, `"place"`, `"thing"`, `"person"`.
- `decidedBy`: `"model"` or `"rules"`.
- `reference`: the earlier passage that explains the phrase. It is **always before** the underlined sentence, never at or after it.

iRead saves these fields to disk and to iCloud, and sends `kind`, `decidedBy` and the engine version with every rating. So they are frozen: never renamed, retyped or removed. A field an engine no longer fills keeps a fixed value instead. `FrozenShapeTests` fails if the shape changes.

**The stream (`underlines(inChapter:of:startingAt:)`)**
- One `UnderlineBatch` per paragraph, starting at the paragraph that holds `sentence`, going to the chapter's end, then wrapping to its start. The reader's page comes first.
- It ends when the chapter is done, or as soon as the consumer stops reading.

**For debugging only**
- `summary` and `ConsideredPhrase.detail` are free text for a debug screen. Their wording is **not** part of the contract, and an app must not parse them.

**Presets**
- `.release`: what the engine ships. Today R8, rules only, contextual embedding.
- `.testing`: the same method with an embedding that needs no download, for tests that must not wait.

## 3. Three kinds of change

| Kind | Example | Version tag | `Linker.version` | iRead must |
|---|---|---|---|---|
| **Pipeline, same output** | Faster search, refactor, cleanup | patch: `1.2.1` → `1.2.2` | unchanged | bump the pin only |
| **Pipeline, different underlines** | New rule, new knob values, new method behind `.release` | minor: `1.2.x` → `1.3.0` | **bump** | bump the pin and regenerate the seeds |
| **Contract change** | Anything in §1 or §2 | major: `1.x` → `2.0.0` | bump if the output changes | change its own code |

When unsure whether underlines change, run the book run (`bookRun` in the README) before and after. If any underline differs, it's the second row.

## 4. Why `Linker.version` matters to iRead

iRead saves the engine version with every chapter it underlines. When it opens a chapter saved with a different version, it underlines that chapter again. So bumping the version means:

- **Every bundled seed is ignored** until it is regenerated, and each chapter is worked out on the reader's device instead (about 8 s a chapter).
- **The hand-made seed** (The Adventures of Sherlock Holmes) can't be regenerated by the engine. After a bump, the engine's own underlines replace it.
- Chapters a reader already has, on the device or in iCloud, are underlined again.
- Ratings carry the version, so ratings from before and after a bump can be told apart.

Forgetting to bump is worse: iRead keeps the old underlines and nobody sees the new behaviour.

## 5. Rules

1. **Never change `Sources/UnderlineKit/` in the same commit as pipeline work.** A contract change gets its own commit and its own PR, so it can be reviewed as one.
2. **Never edit `ContractTests` or `FrozenShapeTests` to make them pass.** If they fail, the contract changed. Decide whether that was intended, and if so treat it as a major change.
3. **A change in meaning is a contract change**, even with the same types: local instead of global indexes, characters instead of UTF-16, a new `kind` string.
4. **Write meaning down in the doc comments** of `Sources/UnderlineKit/`, the way `UnderlineResult` already does. This file and those comments must agree.

## 6. Releasing a change

1. `swift test`. `UnderlineKitTests` must pass unchanged (rule 2).
2. Decide the kind of change (§3). Bump `Linker.version` if underlines change.
3. Update the version in the README's title.
4. Merge to `dev`, then tag the merge commit with the new version.
5. Tell iRead which kind of change it is.

## 7. Upgrading iRead to a new engine

1. **Read the contract diff first:**
   `git diff <old commit> <new commit> -- Sources/UnderlineKit`
   Empty means a pipeline-only change. Anything else, read it against §2.
2. **Bump the pin** in iRead's `project.yml` (`revision:`, with the tag in the comment), run `xcodegen generate`, open the project once so Xcode re-resolves, and commit `project.yml` and `Package.resolved` together.
3. **If `Linker.version` changed, regenerate the seeds:** in iRead's debug sheet, run "Underline whole book" for each sample book, "Export saved chapters", and copy the files into `App/Resources/UnderlineSeed/<book fingerprint>/`.
4. **Run iRead's `Unit` test plan.**
5. **Open one book** and check that underlines appear and that the seeded books show theirs right away. The tests use `.testing`; only the app runs `.release`.

## 8. Known gaps

- **`UnderlineEngine`'s types are `public`**, and the package still offers `UnderlineEngine` as a library product. An app could import it and skip this contract. Fix: make them `package` (visible inside this package only), make `Underliner.init(method:)` `package` too, and drop the `UnderlineEngine` product.
- **iRead's own tests run the real engine** (`.testing`), so a pipeline change can change iRead's test results. Switching iRead's repo tests to `StubUnderliner`, with one test left on the real engine, would separate the two.
- **`1.2.1` isn't tagged yet.** iRead pins commit `3a2efb5` on `dev`.
